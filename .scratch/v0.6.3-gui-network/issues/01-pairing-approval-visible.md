# 01: 配对对话框的接受按钮在最小窗口下无需滚动即可见

> *This was generated by AI during triage.*

**What to build:** 当配对对话框里出现待批准请求（或已连接待确认的 live 配对）时，操作者无需滚动就能看到并使用接受/拒绝（或对应）按钮，即使窗口处于最小尺寸。

**Blocked by:** 无

**Category:** bug
**Status:** ready-for-agent

## Agent Brief

**Category:** bug
**Summary:** 待批准卡片排在二维码与 live 卡片之后，在窄窗口里接受按钮落到折叠线以下。

**Current behavior:**
- 配对对话框按“邀请（200px 二维码、URI、指纹、倒计时）→ live 配对 → 待批准请求 → 设备列表”的顺序排列，整个 body 可滚动。
- 窗口默认 420×640，最小 380×560。出现待批准请求时，接受/拒绝按钮在可视区之外，操作者必须滚动才能看到并点击。

**Desired behavior:**
- 存在待批准请求时，第一个待批准卡片的接受/拒绝按钮在最小窗口尺寸（380×560）下无需滚动即可见。
- 存在 live 配对（客户端已连接但尚未确认）时，其配对码保持可见。
- 没有待批准/live 请求时，二维码邀请仍按现状完整展示并可扫描。
- 多个待批准请求时，第一张卡片的操作可见，其余可滚动；不要求全部同时可见。
- 邀请内容可以缩小、折叠或移到待批准卡片之后，但不得牺牲无请求时的二维码可扫性。

**Key interfaces:**
- 配对对话框视图的区块顺序与布局；不改变后端命令。
- 待批准请求模型中的 `approvalId`、`displayName`、`clientId`、`address`、`sas` 字段保持不变。
- 接受/拒绝动作的命令与参数保持不变。

**Acceptance criteria:**
- [ ] 在 380×560 与 420×640 下，存在一个待批准请求时，接受与拒绝按钮无需滚动即可见、可点击。
- [ ] 存在 live 配对时，其配对码无需滚动即可见。
- [ ] 没有待批准/live 请求时，二维码仍完整显示并可扫描。
- [ ] 多个待批准请求时，第一张卡片的按钮无需滚动即可见；其余可滚动。
- [ ] 键盘焦点顺序仍能到达关闭、接受、拒绝；不引入焦点陷阱回归。
- [ ] `svelte-check` 与生产构建通过。
- [ ] 在 Windows 真机上复验并记录证据；无法复验时记 `NOT RUN`，不得用代码推断冒充 `PASS`。

**Out of scope:**
- 修改窗口默认尺寸或最小尺寸。
- 重新设计对话框其余部分（二维码尺寸、设备列表样式）。
- Rust/后端改动；改变接受/拒绝的业务语义。
