# 01: Windows CI 的 as-cmd replay 测试偶发 UDP 绑定失败

> *This was generated by AI during triage.*

**What to build:** 让 Windows CI 上的 `as-cmd` replay 测试不再因操作系统拒绝某个临时 UDP 端口而偶发失败；失败时必须给出可诊断的信息，而不是连接超时。

**Blocked by:** 无

**Category:** bug
**Status:** ready-for-agent

## Agent Brief

**Category:** bug
**Summary:** 测试选中的 UDP 端口在 Windows runner 上可能落在被排除/禁止的范围内，`bind` 返回 WSAEACCES 10013，测试随后以连接超时失败。

**Current behavior:**
- CI 运行 [45302650376](https://github.com/W0n9/audio-share/actions/runs/45302650376) 的 `Rust (windows-latest)` job，在 `Test workspace` 步骤失败：
  ```
  as-cmd: cannot start the server: bind UDP socket: An attempt was made to access a socket in a way forbidden by its access permissions. (os error 10013)
  ```
- 失败测试：`crates/as-cmd/tests/replay_fixture.rs::harness_replay_of_the_linux_v034_fixture_passes_against_as_cmd`。
- `bind=127.0.0.1:64308` 是测试侧选出的临时端口；Windows 上该端口可能被 Hyper-V/WinNAT 的排除端口段占用或禁止绑定，于是 server 启动失败，测试在 10 秒后以 `os error 10061` 连接被拒结束。
- 同一提交的 `Windows portable packaging`、`Linux deb/AppImage packaging`、`Rust (ubuntu-24.04)` 均成功；用 `gh run rerun --failed` 重跑后 `Rust (windows-latest)` 通过。v0.6.2 发布 CI 也曾通过同一测试。

**Desired behavior:**
- 测试在 Windows 上遇到 WSAEACCES 10013 时，换一个端口重试，而不是直接失败；重试次数用尽后，以“端口被 Windows 排除/禁止”作为明确原因报告。
- 不得把真正的绑定失败（例如端口被占用、非法地址）一并吞掉或误判为可重试。
- Linux 行为保持不变。
- 端口选择/重试逻辑有可测试的 seam；测试注释说明 Windows 排除端口段的存在与原因。

**Key interfaces:**
- `as-cmd` 测试中负责选择/传递 `--bind` 端口的辅助函数。
- `as-cmd` 的绑定失败路径与错误分类：需要把 WSAEACCES 10013 与其他 bind 错误区分开。
- 如果 `as-cmd` 已支持端口 0 并输出实际绑定端口，优先使用该机制；不要仅为测试新增产品 CLI 表面。

**Acceptance criteria:**
- [ ] 在 Windows CI 上，测试遇到 10013 时会换端口重试；重试耗尽时输出明确的端口被禁止诊断，而不是只报连接超时。
- [ ] 非 10013 的绑定失败不会被重试逻辑掩盖。
- [ ] Linux 上测试行为与耗时不变。
- [ ] 端口选择/重试逻辑有单测或其他可重复的验证；若不可单测，说明为什么并用 CI 运行作为证据。
- [ ] 至少一次 Windows CI 运行记录 `PASS`；若需重跑才通过，如实记录。
- [ ] 测试/辅助函数注释说明 Windows 排除端口段（Hyper-V/WinNAT）与 10013 的关系。

**Out of scope:**
- 改变产品的 `--bind` 语义或默认端口。
- 更换 Windows runner 镜像或给整个 CI 加统一 retry。
- 修改 replay fixture、协议行为或 `as-cmd` 的配对/播放逻辑。
- 隐藏或跳过该测试。
