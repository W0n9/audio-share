# Acceptance matrix — new Server over the v0.3.4 Wire Protocol (ticket 15)

Date: 2026-11-09. Environment: Ubuntu 24.04.5 x86_64, Rust 1.98.1,
libpipewire 1.0.5, WirePlumber 0.4.17, release binaries
`target/release/as-cmd` and `target/release/protocol-harness` built from this
branch. Headless `scripts/pw-test-session.sh` session: one `TestSink` null
`Audio/Sink` (`priority.session=1000`, stereo), 440 Hz tone generated by
`scripts/gen-tone-wav.py` and looped into it (30 s WAV at 48 kHz and 44.1 kHz).
No real audio hardware was involved.

Status: **PASS** — 20/20 encoding/channel/rate combinations and 6/6 scripted
scenarios. This proves the server side of the frozen protocol; the real
v0.3.4 APK remains a separate, not-executed gate
(`android-v034-acceptance.md`).

Windows 11 addition (2026-11-10): a real-hardware subset was executed on a
Realtek render endpoint with a 440 Hz WebView2 tone — default/f32/s8/s16/s24/s32
capture, six A/B cases against the released v0.3.4 `as-cmd.exe`, and a 10 s
`protocol-harness probe` (1,998 datagrams, alignment/MTU OK, 0 heartbeat
misses, tone present). Mono at the mix rate is rejected by this driver at
`Initialize` (readable error now), matching the old server's inability to
capture it. See `capture-windows.md` and `build-windows.md` for the Windows
evidence.

## Protocol checks applied to every combination

For each row the probe performed the full Android Client flow: TCP connect,
`GET_FORMAT` (command 1 + u32 length + protobuf), `START_PLAY` (command 2 +
positive id), UDP bind with the id as `i32 LE`, heartbeat replies, and raw PCM
receive. It reported the **actual negotiated** format; the requested format is
shown separately and was never assumed.

- `AudioFormat` bytes and `GET_FORMAT` framing were valid; examples
  (hex `0100000008000000` + protobuf):
  - f32 mono 48 kHz: `0100000008000000080110011880f702`
  - f32 stereo 48 kHz: `0100000008000000080110021880f702`
  - s8 stereo 48 kHz: `0100000008000000080210021880f702`
  - s16 stereo 48 kHz: `0100000008000000080310021880f702`
  - s24 stereo 48 kHz: `0100000008000000080410021880f702`
  - s32 stereo 48 kHz: `0100000008000000080510021880f702`
  - f32 stereo 44.1 kHz: `01000000080000000801100218c4d802`
- `START_PLAY` id was `1` for every fresh server and remained positive.
- UDP bind succeeded and PCM datagrams arrived for every combination.
- Every datagram was `<= 1464` bytes (the `aligned_payload_bytes` was 1464 for
  all rows) and a multiple of the negotiated `block_align`.
- PCM was non-empty; the Goertzel scan found the 440 Hz tone (detected
  440.0 Hz in every row) above the 0.01 threshold and far above the 1000 Hz
  control. Amplitude varies (0.09-0.25) with resampling/startup transients on
  this null-sink graph; presence was still unambiguous.
- One server heartbeat was observed in the 4 s window with zero heartbeat
  misses.

## A/B coverage

The same run executed the A/B subset (48 kHz stereo, 2 s probe) against the old
`as-cmd` 0.3.4 Linux binary. Full details are appended to
`docs/server-rewrite/ab-linux.md`. Summary:

- f32/s16/s24/s32: identical `AudioFormat`/`GET_FORMAT` bytes, `block_align`,
  1464-byte maximum datagram, 440 Hz tone, and near-identical datagram
  distribution; PCM is **not** claimed byte-identical.
- s8: the old binary exits 1 (`U8` negotiation defect documented in
  `ab-linux.md`); the new server serves s8 correctly (`block_align=2`).
- The old binary ignores SIGINT (the A/B teardown uses SIGTERM); the new
  server stops gracefully on SIGINT. This is a test-harness difference, not a
  protocol difference.

## Caveats

- Headless null sink only. Real hardware, real session managers, hotplug, and
  suspend/resume are not covered here (`hotplug-sleep.md`).
- The 4 s window proves startup negotiation and steady streaming, not
  long-duration drift; the release soak (`soak.md`) covers 12 minutes and a
  full 8-hour run (PASS).
- Tone amplitude varies between runs because PipeWire resamples the 48 kHz
  tone file for 44.1 kHz capture and because the probe may start mid-buffer;
  frequency and presence are stable. Do not compare amplitude across rows as
  a level benchmark.
- The real v0.3.4 Android Client is not involved in any row. See
  `android-v034-acceptance.md`; its checkbox remains unchecked.
